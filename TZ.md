# Техническое задание

## Мини-приложение MAX «Маршруты»

Трек: «Досуг и развлечения». Актуализация: 29.09.2026.

Основание - PDF «Досуг и развлечения»: задача и ограничения (стр. 6-8), формат сдачи (9-10), критерии оценки (12-14), рекомендации к сценарию и приоритизации (15-17). Документ описывает существующую реализацию и требования к её проверке. Статус «реализовано» означает наличие функции в коде; работа в опубликованном MAX и на конкретных устройствах подтверждается приёмкой, а не этим статусом.

## 1. Пользователь, проблема и границы MVP

**Приоритетный сегмент:** турист, впервые приехавший в Казань на один день и желающий выбрать самостоятельную прогулку с понятной примерной стоимостью посещения мест. Вторичный сегмент - житель города, планирующий досуг на выходной. Каталог технически поддерживает другие города; демонстрационные маршруты имеются в Казани и Москве.

**Проблема и допущение:** пользователь собирает последовательность мест и цены из разрозненных источников. Предположение о значительных затратах времени требует проверки: в проекте нет интервью, измерений или исследования спроса. До пилота провести наблюдение за выбором прогулки целевыми пользователями и отделить полученные факты от гипотез.

**Полезный результат:** выбранный маршрут, описание и порядок мест, примерная сумма расходов на эти места, карта с пешеходной линией. Полная стоимость поездки, расписания, доступность объектов, время прохождения и бронирование в результат MVP не входят.

**Основной путь:** бот MAX -> выбор города -> список маршрутов -> описание и места -> карта -> план прогулки. Лайк и отправка ссылки дополняют этот путь. Создание собственного маршрута - дополнительный сценарий.

Мини-приложение подключается к боту и должно быть проверяемо в мобильном и веб-MAX. Обычный браузер используется для локальной проверки и разработки. PDF не требует реализовать все примеры досуговых сервисов: MVP сфокусирован на прогулках.

## 2. Авторизация и состояние

Отдельной регистрации, паролей и личного кабинета нет. Просмотр городов, маршрутов и мест доступен без авторизации через API и обычный браузер.

- `client/public/index.html` подключает MAX Bridge; `services/Max/Max.js` получает `initDataUnsafe.user.id`, `initData` и `start_param`.
- Клиент сохраняет id и строку данных запуска в Store и отправляет `X-Max-Init-Data` с запросами при наличии строки.
- С заданным `BOT_TOKEN` сервер получает id только из подписанных данных. HMAC-SHA256 проверяется в `AuthManager.js`: ключ `HMAC-SHA256('WebAppData', BOT_TOKEN)`, затем подпись отсортированных параметров без `hash`. Повторяющиеся ключи отклоняются.
- Возраст данных ограничен 24 часами. Дата из будущего в текущем коде не отклоняется. Это ограничение реализации, а не обещание полной проверки времени.
- Без `BOT_TOKEN` сервер доверяет id из запроса: `user` для просмотра с состоянием лайка, `user_id` для лайка, `route.author_id` для публикации.
- В режиме `npm start` вне MAX клиент использует `dev-user`; продакшен-сборка этого не делает. Кнопка лайка без id недоступна.
- При `ALLOW_ANONYMOUS_ROUTES=true` сервер допускает автора `anonymous`, если подтверждённый id не получен. Для рабочего запуска требуется `false`.
- Черновик, точки, выбранная сортировка и страница сохраняются только в памяти Store. После перезагрузки страницы теряются.

Алгоритм подписи сопоставлен с [официальной документацией MAX](https://dev.max.ru/docs/webapps/validation). Параметры и поддержка интерфейса: [MAX Bridge](https://dev.max.ru/docs/webapps/bridge). Перед сдачей проверить актуальные версии платформы и [историю изменений](https://dev.max.ru/docs/changelog-platform).

## 3. Функциональные требования и фактическое поведение

### 3.1. Выбор города - реализовано

- Список городов загружается через `GET /api/getCities`.
- Поиск показывает подсказки с регионом; доступны касание и клавиатура. «Далее» требует выбранного города.
- Геолокация используется через `navigator.geolocation`, а не через MAX Bridge. Ближайший город определяется по расстоянию до координат центра города. Ранее сделанный выбор не перезаписывается.
- Отказ в геолокации оставляет ручной выбор. Геолокация требует разрешения и защищённого контекста.
- При загрузке поле неактивно; при обработанном ответе API с ошибкой доступны сообщение и «Повторить».
- Если `start_param` начинается с `route_`, после загрузки городов запрашивается маршрут, определяется его город и открывается просмотр. Повторная обработка ссылки в той же сессии блокируется флагом Store.

Выбора города на карте нет. При неудачном запросе маршрута по ссылке нет отдельного экрана ошибки ссылки; при обработанном отказе остаётся выбор города.

### 3.2. Список маршрутов - реализовано

- Заголовок города и «Сменить город».
- Сортировки: `date` («Новые»), `likes` («Популярные»). При равенстве лайков сначала новые; при другом строковом `sort` сервер использует сортировку по дате.
- Карточка: обложка, подпись фото при наличии, название, стоимость, лайк и «Подробнее». Нулевая стоимость обозначается как «Бесплатно».
- Пагинация по 10, кнопки и число страниц при количестве страниц больше одной. Для пустого города показывается пустое состояние; API возвращает `pagesCount=0`.
- Сортировка и страница восстанавливаются из Store. Смена сортировки и подтверждение города сбрасывают страницу на первую.
- Ответы запросов размонтированного/сменившегося экрана игнорируются. Есть индикатор загрузки и повтор при обработанной ошибке API.
- «+» открывает создание маршрута.

Нет фильтров по бюджету, категории или длительности и перехода в кабинет.

### 3.3. Просмотр маршрута и карточка места - реализовано

- Название, авторское описание (`title`), общая цена, обложка и подпись фото, дата публикации при наличии.
- Примечание «Цены примерные и указаны автором маршрута».
- Пронумерованный список мест в порядке добавления; открытие карточки места.
- Карточка места: фото и подпись при наличии, название, номер, цена, описание, «Показать на карте», закрытие.
- «Карта маршрута» недоступна без загруженных мест. При обработанной ошибке загрузки мест показывается сообщение, кнопки «Повторить» на этом экране нет.
- Лайк обновляет локальное состояние и число лайков после ответа сервера.
- «Поделиться» показывается, если доступен `WebApp.shareMaxContent` и задан `BOT_NAME`. Передаёт текст и ссылку `https://max.ru/<BOT_NAME>?startapp=route_<guid>`.

Нет имени автора маршрута, группировки по дням, категории места и галереи фотографий. Сквозная отправка и открытие ссылки требуют проверки двумя пользователями в MAX; отмена отправки отдельно не обрабатывается.

### 3.4. Карта просмотра - реализовано

- 2GIS MapGL с метками, пронумерованными по порядку мест.
- Для двух и более мест запрашивается пешеходный путь через `@2gis/mapgl-directions`.
- При открытии всего маршрута масштаб подгоняется под точки; при переходе из карточки карта центрируется на выбранном месте.
- Переключатель скрывает линию, сохраняя метки. Нажатие на метку открывает карточку места.
- Есть возврат к маршруту и сообщение об ошибке загрузки библиотеки/создания карты.

Доступность построения линии зависит от ключа, покрытия и сервиса 2GIS; длина и время пути в интерфейсе не отображаются. Обработка всех ошибок асинхронной прокладки пути не реализована.

### 3.5. Создание маршрута - частично реализовано

**Экран описания (`CreateRoutePage`):**

- Название и описание обязательны; город подставлен из выбора и недоступен для изменения.
- Обложка необязательна; выбор JPEG, PNG, WebP.
- «Далее» записывает название, описание и выбранный файл в Store и открывает редактор точек.
- Переключатель длительности есть, но значение не записывается в Store, API и базу. Форма показывает «Шаг 1 из 3», хотя отдельного третьего экрана нет.

**Редактор точек (`EditRoutPage`):**

- Карта с центром на выбранном городе.
- «Добавить место» включает выбор координат кликом/касанием; повторное нажатие отключает выбор. Есть подсказка выбора.
- Окно «Новая точка»: обязательны название и средний чек от 0, описание и фото необязательны; доступны сохранение и отмена.
- После сохранения место добавляется в список с номером и координатами и на карту. Метки редактора имеют одинаковый значок без номера.
- «Сбросить» удаляет все точки черновика; изменение/удаление отдельной точки и перестановка не поддерживаются.
- Между двумя и более точками строится пешеходная линия, её можно скрыть.
- «Назад к описанию» сохраняет добавленные точки в памяти; системная «Назад» сначала закрывает окно новой точки, затем возвращает к описанию.

**Публикация:**

1. Недоступна без точек; на время отправки кнопка блокируется и показывает «Публикуем…».
2. Обложка и фото точек загружаются через `/api/uploadImage`.
3. Клиент вычисляет сумму `price` и отправляет маршрут и места через `/api/addRoute`.
4. После успеха черновик очищается и открывается список с прежними сортировкой и страницей. Чтобы увидеть новый маршрут первым, выбрать «Новые» и страницу 1.
5. При обработанном отказе загрузки или публикации показывается сообщение. Отклонение сетевого `fetch` не перехватывается и может оставить состояние публикации активным.

Нет редактирования опубликованного маршрута, категорий, распределения по дням, ввода подписи автора фото и предупреждения о потере черновика при закрытии.

### 3.6. MAX и бот - реализовано в коде

- Системная `BackButton` подключается через `useMaxBackButton`; кнопки в самом интерфейсе доступны и вне MAX.
- Бот обрабатывает `bot_started` и сообщения пользователей, отвечает приветствием и inline-кнопкой-ссылкой открытия приложения.
- Использует long polling с таймаутом 30 секунд; при HTTP-ошибке повторяет запрос после 5 секунд. При отклонении сетевого запроса процесс может завершиться; Compose использует `restart: on-failure`.
- Токен и ник передаются окружением; без них бот завершает запуск. Необходимо отдельно подключить HTTPS-адрес клиента к этому боту на платформе MAX.

Имя и аватар пользователя в интерфейсе, подтверждение закрытия и дополнительные команды бота не реализованы. Соответствие фактической работы мобильному и веб-MAX подтверждается приёмкой.

## 4. Техническая реализация

| Часть | Текущее устройство |
|---|---|
| Клиент | React 19, CRA, пять экранов в `PageManager`: START, ROUTES, CREATE_ROUTE, EDIT, ROUTE; карта и карточка места встроены в экран маршрута |
| Состояние | Store в памяти; отдельного URL-роутинга и постоянного хранения черновика нет |
| API | Express 5, JSON-ответы, CORS, обработчики и Mediator |
| Данные | SQLite, собственная ORM, параметризованные значения SQL, справочник городов при пустой таблице |
| Фото | Multer, `/uploads`, лимит 5 МБ на файл, разрешены MIME `image/jpeg`, `image/png`, `image/webp` |
| Развёртывание | Три контейнера Compose: client/nginx, server, bot; постоянные тома базы и изображений |

Имя загружаемого файла генерирует сервер, расширение определяется по заявленному MIME. Проверки фактического формата содержимого, авторизации загрузки и квот отсутствуют. Это нельзя описывать как полноценную проверку безопасности изображений.

Входные поля проверяются по основным типам. Сервер не проверяет, что цена неотрицательна, координаты входят в допустимый диапазон, `city_guid` существует и сумма мест равна `route.cost`. Сервер получает цену от клиента. Создание маршрута и запись мест выполняются без общей транзакции.

Локальный запуск, переменные, порты, остановка, тестовый экземпляр и условия внешних интеграций описаны в [README.md](README.md). Время Docker-сборки и готовность внешнего HTTPS-развёртывания этим документом не подтверждаются.

## 5. Модель данных

Схема соответствует `server/application/modules/db/DB.js`. `x` - долгота, `y` - широта. Сервер генерирует UUID v4 для новых маршрутов и мест.

| Таблица | Поля и назначение |
|---|---|
| `cities` | `guid TEXT NOT NULL`, `city TEXT NOT NULL`, `region TEXT`, `x REAL NOT NULL`, `y REAL NOT NULL`; в текущем DDL у города нет объявленного первичного/уникального ключа |
| `routes` | `guid TEXT PRIMARY KEY`, `name TEXT NOT NULL`, `title TEXT NOT NULL` (описание), `cost INTEGER`, `x/y REAL`, `author_id TEXT NOT NULL`, `photo_url TEXT`, `photo_credit TEXT`, `city_guid TEXT`, `created_at INTEGER` (миллисекунды Unix) |
| `places` | `guid TEXT NOT NULL UNIQUE`, `name TEXT NOT NULL`, `x/y REAL NOT NULL`, `price REAL NOT NULL`, `description TEXT NOT NULL`, `route_guid TEXT`, `photo_url TEXT`, `photo_credit TEXT` |
| `likes` | `route_guid TEXT NOT NULL`, `user_id TEXT NOT NULL`, составной первичный ключ `(route_guid, user_id)` |

У `places.route_guid` и `likes.route_guid` объявлены ссылки на `routes.guid`, но включение `PRAGMA foreign_keys=ON` в коде отсутствует. У `routes.city_guid` внешнего ключа нет. Порядок мест определяется `rowid`, а не полем `order_index`. `liked` и количество лайков вычисляются запросом, не хранятся в маршруте.

В текущей модели нет длительности, дня посещения, категории, имени автора и времени постановки лайка. `photo_credit` читается и показывается для стартовых данных; обработчик публикации не сохраняет переданный `photo_credit`.

## 6. API и обработка ошибок

Контракт: [openapi.yaml](openapi.yaml), обязательные проверки: [DATA-API.yaml](DATA-API.yaml), данные: [test-data/test-data.json](test-data/test-data.json). Базовый путь `/api`. Указанный в YAML адрес `https://example.ru/api` - шаблон, который нужно заменить действительным адресом при подготовке сдачи.

Успех: HTTP 200, `{ "result": "ok", "data": ... }`. Ошибка: `{ "result": "error", "error": { "code": ..., "message": "..." } }` с соответствующим HTTP-кодом.

| Метод и путь | Запрос | Ответ / особенности |
|---|---|---|
| `GET /getCities` | Без параметров | Массив городов |
| `GET /chooseCity/:city` | Строка в пути | `true`; не сохраняет выбор и не проверяет существование города. Основной клиентский путь этот метод не вызывает |
| `GET /getRoutes` | `city` обязателен; `page` - целое от 1 (по умолчанию 1); `sort` - строка, `user` - необязательный id для режима разработки | `{ routes, pagesCount }`, до 10 элементов; `likes` и `liked` у маршрута |
| `GET /getRoute` | `route` обязателен, `user` необязателен | Маршрут с `likes`, `liked`; отсутствующий маршрут -> 404, код 25 |
| `GET /getPlaces` | `route` обязателен | Массив мест по `rowid`; неизвестный маршрут -> пустой массив с 200 |
| `POST /addRoute` | `{ route, places }`, непустой массив мест | guid; с выключенным анонимным режимом нужен id пользователя |
| `POST /toggleLike` | `{ route_guid, user_id? }` | `{ liked, likes }`; нужен пользователь, отсутствующий маршрут -> 404 |
| `POST /uploadImage` | `multipart/form-data`, поле `image` | Строка `/uploads/<uuid>.<ext>`; авторизация в текущем обработчике не требуется |

Тело публикации:

```json
{
  "route": {
    "name": "Проверочный маршрут",
    "title": "Описание прогулки",
    "cost": 0,
    "x": 49.10724,
    "y": 55.797442,
    "city_guid": "2f8f462b-7bf7-4c9c-8796-7a1afe7d13c4",
    "photo_url": null
  },
  "places": [
    {
      "name": "Казанский кремль",
      "x": 49.10724,
      "y": 55.797442,
      "price": 0,
      "description": "Пример места",
      "photo_url": null
    }
  ]
}
```

`route.author_id` нужен при проверке публикации в режиме разработки без `BOT_TOKEN`. В защищённом режиме id извлекается из `X-Max-Init-Data`; отдельного логина и пароля нет. Публичное чтение не требует этого заголовка.

| Код | HTTP | Сообщение в текущем `Answer.js` |
|---|---|---|
| 11 | 401 | Ошибка авторизации |
| 25 | 404 | Маршрут не найден |
| 67 | 400 | Не переданы все необходимые параметры |
| 68 | 400 | Не удалось загрузить изображение |
| 69 | 400 | Некорректное тело запроса |
| 404 | 404 | Метод не найден |
| 9000 | 500 | Самая страшная ошибка |

Обработчик Express преобразует ошибки в предусмотренный JSON. Однако обещать повтор после любого сбоя нельзя: отклонение `fetch` на клиенте не перехватывается, повтор реализован только на отдельных экранах для обработанных ответов.

## 7. Данные, происхождение и актуальность

Проверена поставляемая база: 1117 городов, 15 маршрутов/51 место в Москве, 10 маршрутов/32 места в Казани, 0 лайков. Суммы цен мест совпадают с ценой маршрутов. Все используемые локальные фотографии существуют.

Маршруты, места и цены демонстрационные и заранее подготовленные; получение актуальных цен и расписаний не реализовано. Дата проверки базы не означает дату актуальности цен. У пользовательского маршрута сведения задаёт автор вручную.

Фото находятся в `server/public/uploads`. Для стартовых маршрутов и мест в базе заполнены подписи с указаниями авторов, лицензий и Wikimedia Commons; UI их отображает. Отдельного реестра источников `CREDITS.md` в проекте нет. Подтверждение исходных страниц фото, условий лицензий и дат данных - отдельная задача перед публичной сдачей.

Предыдущие документы указывали HFLabs для городов и Викиданные для координат, но отдельного файла подтверждения происхождения в проекте нет. Эти указания не считаются доказанной интеграцией. Для пилота следует зафиксировать источник, территорию, дату проверки и ответственного за обновление каждого набора.

В Docker исходная база копируется в пустой том; повторный запуск использует сохранённые данные. Инструкция проверки на чистых тестовых томах, авторизация тестового пользователя и предупреждение об удалении тестовых данных приведены в README.

## 9. Приёмка и комплектность по PDF

Сценарии запуска и действий с ожидаемыми результатами находятся в README. Приёмка должна выполняться на одной зафиксированной версии кода и исходных тестовых данных.

| Проверка | Критерий приёмки |
|---|---|
| Основной сценарий | В мобильном и веб-MAX пользователь от кнопки бота доходит до выбранного маршрута, карточки места и карты без помощи разработчика |
| Данные | На исходной базе видны 10 маршрутов Казани и две страницы Москвы; карточки и фотографии соответствуют выбранным объектам |
| Лайки | Постановка/снятие работает повторно; значение сохраняется после перезапуска, пользователь без действительной подписи не меняет лайки на защищённом сервере |
| Обмен ссылкой | Получатель в MAX открывает тот маршрут, который отправил другой пользователь; возврат и город корректны |
| Создание | Две точки, фото и сумма цен сохраняются; новый маршрут найден на первой странице «Новые» |
| Хранение | Остановка и повторный запуск сохраняют базу и изображения |
| Ошибки API | Обязательные проверки DATA-API проходят; неверные параметры, отсутствующий маршрут и отсутствие авторизации дают заявленные статусы и поля |
| Ошибки UX | Отказ в геолокации не мешает ручному выбору; обработанные ошибки списков дают повтор. Сетевые сбои проверить отдельно и зафиксировать текущие ограничения |
| Docker | Все локальные компоненты запускаются одной командой, сборка укладывается в 5 минут без загрузки базовых образов |
| Доступность | Реальные HTTPS-адреса клиента/API и бот доступны всё время проверки; шаблоны адресов заменены |

Сдача по PDF требует работающего продукта в MAX, фиксированной версии репозитория (URL + commit hash либо архив с контрольной суммой), README, файлов зависимостей, Docker-конфигурации и презентации PDF. Поскольку проект имеет собственный API, также нужны действительный HTTPS-адрес, OpenAPI 3.0/3.1, тестовые роли и данные, DATA-API с обязательными проверками.

Презентация: первый служебный слайд содержит ссылки, версию, тестовый доступ и необходимые значения окружения; продуктовая часть - команду, резюме, аудиторию и проблему, сценарий, эффект, архитектуру, данные, масштабирование, ограничения и источники. Рабочие секреты в репозиторий не помещаются. Проверить лицензии кода, библиотек и фото. В текущем дереве проекта презентация PDF не обнаружена; доступность опубликованного продукта, результаты платформенной проверки и длительность сборки не подтверждены.

До дедлайна выполнить проверки на сдаваемой версии, записать результаты и идентификатор версии. После дедлайна переданная версия не изменяется; изменения финального этапа явно отражаются в финальной презентации, как требует PDF.

Фактически при актуализации выполнена сверка кода, конфигурации, ссылок, примеров JSON и поставляемой базы. Пробный запуск API на изолированной копии базы не состоялся из-за отсутствующего `multer` в локальном `server/node_modules`; перед проверкой восстановить зависимости. Результаты приёмки API, Docker и MAX пока не получены.

## 10. Пилот, эффект и тиражирование

**Пилот (предложение, не состоявшийся запуск):** однодневные прогулки по Казани. Команда проверяет исходные маршруты, цены и фото, назначает ответственного за содержание и технического сопровождения. Потенциальные партнёры - туристический инфоцентр и местные авторы; договорённостей в проекте не зафиксировано. Доступ - ссылка бота и QR-код в материалах партнёров после согласования.

**Проверка эффекта:** сравнить время выбора прогулки вручную и через приложение на одинаковой задаче. Измерять долю пользователей, завершивших основной путь без помощи, время до выбора, открытия карты, успешные переходы по ссылкам и понятность стоимости. Сбор аналитики не реализован; на пилоте использовать наблюдение и журнал результатов. Целевые значения определить после исходного замера. Нельзя заявлять достигнутую экономию или спрос без результатов.

**Порядок масштабирования:** пилот в Казани -> разбор ошибок и подтверждение ценности -> второй город, например Самара -> расширение каталога. Существующие данные Москвы можно использовать для проверки переноса интерфейса, но не как доказательство действующего пилота.

**Условия адаптации:** сохранить каталог, просмотр, создание, лайки и вход через MAX; подготовить местные маршруты, координаты, стоимость, разрешённые изображения и процесс обновления. Нужны ответственные за данные, модерацию и поддержку, HTTPS-развёртывание и действующие внешние ключи. Новые типы сценариев требуют проверки модели и пользовательского пути.

**Риски роста:** качество и актуальность пользовательского контента, права на фото, лимиты внешних сервисов, публичная загрузка файлов, нагрузка на SQLite и объём изображений. До тиражирования усилить проверки и квоты, ввести модерацию/обновление контента, резервное копирование и измерение нагрузки; замену хранилища планировать по измерениям.
