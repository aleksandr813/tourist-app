# Техническое задание

## Мини-приложение MAX «Маршруты» - поиск и создание туристических маршрутов по городам

Трек хакатона: «Досуг и развлечения»

---

## 1. Общее описание продукта

**Проблема:** пользователь, приезжающий в город на 1–2 дня (или житель, который хочет провести выходные иначе), вынужден самостоятельно собирать маршрут из разрозненных источников - отзывов, карт, блогов - и не может заранее понять, во сколько обойдётся весь день.

**Решение:** мини-приложение внутри мессенджера MAX, в котором:
- пользователи находят готовые туристические маршруты по выбранному городу с указанием общей стоимости;
- каждый маршрут - это последовательность мест (кафе, музеи, смотровые площадки и т.д.) с ценой посещения каждого места;
- пользователи сами создают маршруты, отмечая точки прямо на карте и заполняя информацию о каждом месте вручную (все данные о местах - авторские, без автоматической подгрузки с внешних сервисов).

**Пользователь:** [Житель/турист] в ситуации [приехал в незнакомый город на 1–2 дня / хочет спланировать выходные] хочет [получить готовый маршрут с понятной стоимостью], но сталкивается с [разрозненностью информации о местах и ценах], из-за чего [тратит время на составление плана вручную или переплачивает].

---

## 2. Пользователь

Мини-приложение открывается только внутри мессенджера MAX (через бота) - отдельного веб-входа нет. Поэтому гостевого режима не предусмотрено: при каждом запуске MAX Bridge отдаёт id пользователя в мессенджере, и он используется как идентификатор автора без отдельной регистрации. Любой пользователь может просматривать города, маршруты, места и карту маршрута, а также создавать маршруты, добавлять точки-места на карте и редактировать/удалять свои маршруты.

---

## 3. Функциональные требования

### 3.1 Экран запуска - выбор города

Открывается сразу при запуске мини-приложения.

**Элементы экрана:**
- Заголовок «Выберите город»
- Поле поиска с автодополнением (список городов из собственной базы приложения, фильтрация по вводу)
- Список популярных / ближайших городов под поиском
- Кнопка «Выбрать на карте» - открывает карту, пользователь тапает по региону/городу
- Если MAX Bridge отдаёт геолокацию устройства - приложение автоматически определяет ближайший город (по расстоянию до центра города из своей базы городов) и **предзаполняет** его как выбранный, но пользователь может изменить выбор.
  - Если геолокация недоступна или пользователь её не разрешил - показывается просто список городов без автовыбора, курсор в поле поиска.

**MVP-упрощение (если не успеваем с полноценным поиском на карте):** оставить только список + поиск текстом, кнопку «на карте» вынести в Should Have.

**Текущий статус реализации:** вместо поиска с автодополнением и списка городов сейчас реализован временный выпадающий список (`<select>`), заполняемый через `GET /api/getCities`; выбор подтверждается через `GET /api/chooseCity/:city`. Автодополнение, геолокация через MAX Bridge и кнопка «Выбрать на карте» пока не реализованы.

---

### 3.2 Главный экран - список маршрутов по городу

**Элементы:**
- Шапка: название выбранного города + иконка «изменить город» (возврат на экран 3.1)
- Список карточек маршрутов, для каждой:
  - превью-фото (обложка маршрута)
  - название маршрута
  - суммарная цена маршрута (например, «≈ 2 400 ₽»)
  - короткий тег/длительность (например, «1 день», «2 дня»)
- Кнопка/FAB «+ Добавить маршрут» - открывает меню редактирования маршрутов (см. 3.6)
- **Should Have:** сортировка по цене (по возрастанию/убыванию) - переключатель или иконка сортировки сверху списка
- **Could Have:** фильтр по длительности (1 день / 2 дня), по категориям (гастро, культура, активный отдых)

Если маршрутов для города нет - пустое состояние с текстом «Пока нет маршрутов в этом городе» и кнопкой «Создать первый маршрут».

**Текущий статус реализации:** список маршрутов пока отображает статичные тестовые данные, захардкоженные во фронтенде (`RoutesPage.js`) - запрос к бэкенду за маршрутами конкретного города ещё не подключён (соответствующий эндпоинт `GET /api/cities/:id/routes` из раздела 6.2 не реализован).

---

### 3.3 Экран маршрута - подробная информация

**Элементы сверху вниз:**
- Обложка маршрута (фото)
- Название маршрута
- Автор (имя пользователя, создавшего маршрут)
- Описание от автора (текст произвольной длины - что это за маршрут, для кого, советы)
- Суммарная цена маршрута
- Длительность (1/2 дня)
- Кнопка **«Карта маршрута»** - открывает карту (см. 3.5)
- Список **блоков мест**, в порядке посещения:
  - блок = фото места + название + цена (средний чек / билет / «бесплатно»)
  - нумерация блоков по порядку (1, 2, 3…), чтобы был понятен маршрут во времени
  - тап по блоку → открывает карточку места (3.4)
- Если маршрут состоит из нескольких дней - блоки визуально сгруппированы по дням («День 1», «День 2»)

---

### 3.4 Карточка места (подробная информация)

Открывается по тапу на блок места.

**Элементы:**
- Фото (или галерея, если несколько) - загружено автором маршрута
- Название места - введено автором
- Категория (кафе / музей / смотровая / парк и т.д.) - выбрана автором из справочника категорий приложения
- Цена (средний чек / стоимость билета / бесплатно) - введена автором
- Описание - введено автором
- Кнопка «Показать на карте» - открывает карту с одной меткой этого места (координаты - это единственное, что связано с картой: точка, которую автор указал при создании)

Все данные о месте - авторские; внешние источники (Яндекс.Карты, справочники организаций и т.п.) для заполнения карточки не используются, поэтому в карточке не нужна отдельная пометка об источнике данных - источник всегда один: пользователь.

---

### 3.5 Карта маршрута

Открывается по кнопке «Карта маршрута» с экрана 3.3, либо для одного места с экрана 3.4.

**Элементы:**
- Карта Яндекс с метками всех мест маршрута
- Метки пронумерованы в порядке посещения (совпадает с порядком блоков)
- Линия/маршрут, соединяющая точки (в MVP - прямые линии между точками; Should Have - построение реального маршрута через `multiRouter.MultiRoute` Яндекс.Карт)
- Тап по метке → всплывающая мини-карточка (название, цена) → переход в карточку места
- Кнопка «Назад» к маршруту

Это **единственная функция карты в режиме просмотра**: показать точки и (по возможности) маршрут между ними. Никакие данные о месте с карты не подтягиваются - они уже целиком хранятся в базе приложения из момента создания маршрута.

---

### 3.6 Режим редактирования маршрута - добавление точек на карте

Это центральный сценарий создания контента в приложении, поэтому продуман отдельно.

**Шаг 1. Общая информация о маршруте**
Форма (один экран со скроллом или первый шаг мастера):
- Обложка маршрута - загрузка фото
- Название маршрута
- Город (по умолчанию - текущий выбранный)
- Описание от автора (текстовое поле)
- Длительность - 1 или 2 дня
- Кнопка «Далее» → переход к режиму расстановки точек

**Шаг 2. Режим карты - расстановка мест**

Открывается карта, центрированная на выбранном городе (просто отображение карты Яндекс, без поиска по организациям).

Взаимодействие:
1. Пользователь **тапает в любую точку карты**, где хочет отметить место.
2. На карте сразу появляется временная метка в этой точке (визуальный отклик, что нажатие зафиксировано).
3. Поверх карты открывается **модальное окно / bottom sheet «Новое место»** с полями:
   - Фото - загрузка с устройства (обязательно)
   - Название места (обязательно)
   - Категория - выбор из справочника (кафе, музей, парк, смотровая площадка, активность и т.д.)
   - Цена - число или переключатель «Бесплатно» (обязательно)
   - Короткое описание / совет от автора (необязательно)
   - Координаты подставляются автоматически (из точки нажатия), пользователю не нужно их вводить - при необходимости можно скорректировать положение точки перетаскиванием метки под окном, пока оно открыто
4. Кнопки внизу окна: **«Сохранить»** и **«Отмена»**.
   - «Сохранить» - место фиксируется, метка на карте становится постоянной и получает порядковый номер (следующий по счёту в маршруте)
   - «Отмена» - временная метка исчезает, ничего не сохраняется
5. Под картой (или в свёрнутом виде снизу, шторкой) отображается **список уже добавленных мест** маршрута - синхронизирован с метками на карте:
   - каждая строка = миниатюра фото + название + цена + номер
   - тап по строке в списке - карта центрируется на этой точке, открывается то же модальное окно, но в режиме **редактирования** (все поля предзаполнены, есть кнопка «Удалить место»)
   - тап по существующей метке на карте - то же самое, открывает редактирование
   - **Should Have:** переупорядочивание мест в списке (drag-and-drop либо стрелки вверх/вниз), если хочется поменять порядок посещения без пересоздания точек
   - **Should Have:** перетаскивание метки на карте для уточнения позиции уже сохранённого места
6. Если маршрут на 2 дня - над списком переключатель/вкладки «День 1» / «День 2»: новые точки добавляются в текущую выбранную вкладку, точки разных дней визуально различаются на карте (например, цветом метки)

**Шаг 3. Публикация**

- Итоговая сумма маршрута считается автоматически (сумма цен всех добавленных мест) и показывается перед публикацией
- Проверка: маршрут должен содержать хотя бы одну точку, иначе кнопка «Опубликовать» неактивна
- Кнопка «Опубликовать»

**Почему так удобнее, чем поиск по организациям:**
- один и тот же интерфейс (тап по карте → форма) работает и для реальных заведений, и для мест, которых нет ни в одном справочнике (смотровая площадка, граффити, живописный двор) - не нужно два разных сценария «нашли в поиске» / «добавили вручную»;
- автор сам решает, в какой точке физически стоять, чтобы сфотографировать/рекомендовать место - это может не совпадать с координатами входа в организацию из справочника;
- никакой зависимости от платных или ограниченных по лимитам API поиска организаций - используется только отображение карты, которое бесплатно в рамках стандартного лимита JS API.

**Should Have:** редактирование и удаление собственных ранее созданных маршрутов (тот же режим редактирования, открытый повторно для существующего маршрута).

## 4. Технические требования

### 4.1 Общая архитектура

- **Frontend:** React, работает как мини-приложение MAX (HTML/JS/CSS, HTTPS), интеграция с платформой через **MAX Bridge** (получение геолокации, платформы запуска и т.д.), интерфейс - на базе **MAX UI**
- **Backend:** Node.js (Express или Fastify) + REST API
- **База данных:** PostgreSQL (+ Prisma как ORM)
- **Карты:** используется исключительно **Yandex Maps JavaScript API** - рендер карты, метки (`Placemark`), обработка клика по карте (`map.events.add('click', ...)`) для расстановки точек, полилиния/`multiRouter.MultiRoute` для отображения маршрута между точками
- Никакие другие продукты Яндекса (Геокодер, Геосаджест, API Поиска по организациям) **не используются** - вся информация о местах вводится и хранится как собственные данные приложения
- **Хранение фото:** файлы принимаются backend'ом (Multer) и отдаются со статики/облачного хранилища; путь к фото хранится в БД

### 4.2 Интеграция с MAX

- Получение идентификатора пользователя через MAX Bridge для авторизации без отдельной регистрации
- Получение геолокации устройства через MAX Bridge (если пользователь разрешил) для предзаполнения города на экране 3.1
- Мини-приложение подключено к чат-боту (не существует изолированно от бота), должно быть доступно и в мобильной, и в веб-версии MAX

### 4.3 Данные и их происхождение

- Все данные о местах (название, фото, цена, описание, координаты) - вводятся пользователями через режим редактирования карты (3.6). Внешние источники для автозаполнения не используются, поэтому разделение «данные из справочника / данные от пользователя» в этой версии продукта не требуется - источник всегда один
- Если для демонстрации используется тестовый набор городов и заранее подготовленных маршрутов - это явно фиксируется в README, как того требует регламент хакатона
- Карта используется только как холст для отображения и как инструмент выбора координат - данные с неё (адреса, названия организаций и т.п.) не считываются и не сохраняются, поэтому ограничение стандартной лицензии Яндекса «нельзя сохранять данные, полученные через API» здесь неприменимо: сохраняются только координаты клика и то, что ввёл сам пользователь, а не какие-либо сведения, предоставленные самим API Яндекса

## 5. Примерная модель данных

```
User
 - id (guid, PK)
 - max_user_id
 - name

City
 - id (guid, PK)
 - name
 - x, y (центр города, для геолокационного дефолта и центрирования карты)

Place
 - id (guid, PK)
 - route_id (guid, FK -> Route)   -- место существует только в контексте маршрута, куда его добавил автор
 - name
 - category
 - x, y                  -- координаты, выбранные автором тапом по карте
 - photo_url
 - price (число или null / "бесплатно")
 - description (nullable)
 - order_index                -- порядок посещения внутри маршрута
 - day_number                 -- 1 или 2, для многодневных маршрутов

Route
 - id (guid, PK)
 - title
 - cover_photo_url
 - description
 - city_id (guid, FK -> City)
 - author_id (guid, FK -> User)
 - duration_days (1 | 2)
 - total_price (вычисляется как сумма Place.price по маршруту)
 - created_at
```

Все первичные ключи — **GUID (UUID v4)**, а не автоинкрементные числа. В PostgreSQL это делается либо расширением `pgcrypto`/`uuid-ossp` с `DEFAULT gen_random_uuid()` на колонке, либо на уровне Prisma-схемы: `id String @id @default(uuid()) @db.Uuid`. Внешние ключи (`route_id`, `city_id`, `author_id`) — тоже GUID, ссылаются на такие же UUID-колонки.

Промежуточная таблица `RoutePlace` из предыдущей версии ТЗ больше не нужна: поскольку места создаются исключительно в контексте конкретного маршрута (а не переиспользуются между разными маршрутами), связь «место - маршрут» встроена прямо в таблицу `Place` через `route_id`.

**Could Have:** если в будущем понадобится переиспользовать одно и то же место в нескольких маршрутах (например, автор делает два маршрута через один и тот же парк), можно вернуться к схеме с отдельной таблицей `Place` (без `route_id`) и связывающей `RoutePlace` - но для MVP это усложнение не требуется.

## 6. API-эндпоинты

Все эндпоинты смонтированы под общим префиксом `/api`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/getCities` | Возвращает список всех городов из БД (без параметра поиска, без пагинации) |
| GET | `/api/chooseCity/:city` | Валидирует и подтверждает выбор города; серверное сохранение выбора за пользователем пока не реализовано |
| GET | `/api/cities?search=` | Поиск городов |
| GET | `/api/cities/nearest?x=&y=` | Ближайший город по координатам |
| GET | `/api/cities/:id/routes?sort=price` | Список маршрутов по городу |
| GET | `/api/routes/:id` | Подробная информация о маршруте (включая места) |
| POST | `/api/routes` | Создание маршрута |
| POST | `/api/routes/:id` | Редактирование общей информации маршрута |
| GET | `/api/routes/:id` | Удаление маршрута |
| POST | `/api/routes/:id/places` | Добавление места в маршрут (координаты + данные из модального окна) |
| GET | `/api/places/:id` | Удаление места из маршрута |
| GET | `/api/places/:id` | Подробная информация о месте |

## 7. Приоритизация функций (MoSCoW)

**Must Have (без этого сценарий не работает):**
- Выбор города (список + поиск)
- Список маршрутов города с ценой и превью
- Подробная страница маршрута с блоками мест и описанием автора
- Карточка места
- Карта маршрута с метками (без построения реального маршрута - просто точки)
- Создание маршрута: режим карты с тапом по точке → модальное окно с полями места → сохранение
- Список добавленных мест, синхронизированный с картой, во время редактирования

**Should Have:**
- Автоопределение города по геолокации из MAX Bridge
- Сортировка маршрутов по цене
- Редактирование/удаление своих маршрутов и отдельных мест в них
- Построение реального маршрута между точками на карте (`multiRouter.MultiRoute`) вместо прямых линий
- Переупорядочивание мест (drag-and-drop) и перетаскивание меток для уточнения координат

**Could Have:**
- Фильтры по категориям и длительности
- Отдельная переиспользуемая база мест вне контекста конкретного маршрута (схема с `RoutePlace`)
- Рейтинги/отзывы на маршруты

**Won't Have (сознательно не делаем в MVP):**
- Бронирование билетов/столиков внутри приложения
- Онлайн-оплата
- Социальные функции (подписки на авторов, лайки, комментарии)
- Любая автоматическая подгрузка данных о местах из внешних справочников/карт

## 9. Открытые вопросы / допущения

- Точный формат получения геолокации через MAX Bridge нужно сверить с актуальной документацией MAX перед реализацией (в брифе явно указано ориентироваться на актуальную документацию, а не на устаревшие примеры)
- Построение маршрута через `multiRouter.MultiRoute` использует клиентский JS API (тот же бесплатный лимит, что и на отображение карты) - отдельного платного HTTP API маршрутизации для этого не требуется; это стоит перепроверить по актуальной документации перед реализацией Should Have пункта
- Модерация пользовательских маршрутов и мест в MVP не предусмотрена (можно добавить в Could Have при наличии времени)
- Стоит продумать защиту от случайных лишних точек при разметке маршрута (например, подтверждение при выходе из режима редактирования без сохранения, если открыто модальное окно с незаполненными обязательными полями)
